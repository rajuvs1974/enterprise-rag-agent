# Spec 002 — Persistence Layer Implementation Plan

**Specification:** `002-persistence/spec.md`
**Status:** Draft
**Version:** 1.0

---

## 1. Implementation Objective

Implement a PostgreSQL-backed persistence layer that provides reliable storage for enterprise document metadata, document lifecycle state, versions, authorization metadata, processing jobs, indexing state, tenants, and audit events.

The implementation MUST preserve the cloud-neutral architecture defined in the project constitution.

---

# 2. Architectural Approach

The persistence implementation will follow a layered architecture:

```text
API
 │
 ▼
Application Services
 │
 ▼
Domain / Repository Interfaces
 │
 ▼
Infrastructure
 │
 ├── SQLAlchemy
 │
 └── PostgreSQL
```

The application layer MUST NOT directly depend on SQLAlchemy models or database sessions.

---

# 3. Technology Selection

## Database

**PostgreSQL**

Reason:

* mature relational database
* strong transactional guarantees
* excellent indexing capabilities
* JSON support
* strong ecosystem
* suitable for enterprise metadata
* portable across AWS and Azure
* available locally through Docker

PostgreSQL will remain the system of record.

---

## ORM

**SQLAlchemy 2.x**

Use SQLAlchemy's modern typed API.

Reasons:

* mature ecosystem
* explicit transaction management
* strong PostgreSQL support
* asynchronous support
* good migration ecosystem
* compatible with cloud-managed PostgreSQL

---

## Migration Tool

**Alembic**

Database schema changes MUST be version controlled through migrations.

Developers MUST NOT rely on manually created production tables.

Migration flow:

```text
Model Change
     ↓
Alembic Migration
     ↓
Review
     ↓
CI Validation
     ↓
Deployment
```

---

## Database Driver

Use PostgreSQL's supported async driver through SQLAlchemy's async engine.

The application should use asynchronous database access where appropriate because the platform will be highly I/O-oriented.

---

# 4. Domain Model

The initial domain entities are:

```text
Tenant
Document
DocumentVersion
DocumentACL
ProcessingJob
AuditEvent
```

The domain layer SHOULD use Pydantic models where appropriate for data contracts.

Database-specific SQLAlchemy models MUST remain in the infrastructure layer.

---

# 5. Domain vs Persistence Models

We will deliberately separate:

```text
Domain Model
     │
     │ mapping
     ▼
Persistence Model
```

Example:

```text
domain.document.Document
             │
             ▼
infrastructure.persistence.models.DocumentModel
```

This prevents database implementation details from leaking into business logic.

---

# 6. Repository Interfaces

Define repository interfaces in the application/domain boundary.

Initial interfaces:

```text
TenantRepository
DocumentRepository
DocumentVersionRepository
DocumentACLRepository
ProcessingJobRepository
AuditRepository
```

Interfaces SHOULD define business-oriented operations rather than generic SQL operations.

Avoid exposing methods such as:

```text
execute_sql()
run_query()
```

Prefer:

```text
get_by_id()
get_by_external_id()
create()
update_status()
list_versions()
create_job()
```

---

# 7. Database Session Architecture

Create a database session factory in infrastructure.

Conceptually:

```text
Application
    │
    ▼
Repository
    │
    ▼
AsyncSession
    │
    ▼
PostgreSQL
```

Session lifecycle MUST be controlled by the application/infrastructure boundary.

Sessions MUST NOT be stored globally.

---

# 8. Transaction Management

Transactions MUST be explicit.

For example:

```text
Create Document Version
        │
        ▼
BEGIN
        │
        ├── insert document version
        ├── update document
        └── create processing job
        │
        ▼
COMMIT
```

If any operation fails:

```text
ROLLBACK
```

The application MUST NOT leave partially committed database state for a logical transaction.

---

# 9. Schema Design

Initial tables:

```text
tenants
documents
document_versions
document_acls
processing_jobs
audit_events
```

Potential future table:

```text
index_sync_state
```

This may initially be represented through document/version processing state rather than introducing unnecessary schema complexity.

---

# 10. Primary Keys

Use UUID identifiers.

Recommended approach:

```text
UUID
```

Identifiers will be generated by the application or database according to the final implementation decision.

The identifier strategy MUST remain portable across AWS RDS PostgreSQL and Azure Database for PostgreSQL.

---

# 11. Tenant Isolation

Every tenant-owned record MUST have a tenant relationship.

At minimum:

```text
documents.tenant_id
audit_events.tenant_id
```

Other entities derive tenant ownership through their parent relationships where appropriate.

Repository operations SHOULD require tenant context where tenant isolation is relevant.

Example:

```python
get_document(
    tenant_id=tenant_id,
    document_id=document_id,
)
```

rather than:

```python
get_document(document_id)
```

---

# 12. Document Identity

Document identity consists of:

```text
Internal document ID
+
Tenant ID
+
Source
+
External ID
```

Recommended uniqueness constraint:

```text
UNIQUE(
    tenant_id,
    source,
    external_id
)
```

This prevents duplicate logical documents from the same source within a tenant.

---

# 13. Document Version Strategy

Versions are immutable.

Example:

```text
documents
    │
    ├── version 1
    ├── version 2
    └── version 3
```

A new source version creates a new `document_versions` record.

The current version is referenced from the logical document.

Previous versions remain available for audit and reproducibility subject to retention policy.

---

# 14. Tombstone Strategy

Deletion will initially use logical deletion.

Example:

```text
ACTIVE
  │
  ▼
TOMBSTONED
```

The document record remains in PostgreSQL.

The deletion event is recorded in `audit_events`.

Search indexing will consume the deletion event and remove or deactivate the derived search representation.

Physical deletion may be introduced later through retention policies.

---

# 15. Processing Jobs

Document processing will be asynchronous.

Example:

```text
Document Version
      │
      ▼
Processing Job
      │
      ├── PARSE
      ├── CHUNK
      ├── EMBED
      └── INDEX
```

Jobs will track:

* status
* attempt
* timestamps
* errors

This provides the foundation for future SQS/Azure Service Bus integration.

---

# 16. Index Synchronization

PostgreSQL is authoritative.

OpenSearch is derived.

Example:

```text
PostgreSQL
    │
    ▼
Processing Event
    │
    ▼
OpenSearch
```

If OpenSearch becomes inconsistent, the platform must be able to determine which records require reindexing.

A future reconciliation worker will compare authoritative PostgreSQL state against search-index state.

---

# 17. Audit Strategy

Audit events will be append-only.

Example:

```text
DOCUMENT_CREATED
DOCUMENT_UPDATED
DOCUMENT_TOMBSTONED
DOCUMENT_INDEXED
DOCUMENT_INDEX_FAILED
ACL_CHANGED
```

Audit metadata will use PostgreSQL JSON/JSONB where flexible event-specific attributes are required.

Sensitive document content MUST NOT be stored in audit metadata.

---

# 18. Error Mapping

Database errors will be translated at the infrastructure/application boundary.

Examples:

```text
UniqueViolation
      ↓
DocumentAlreadyExistsError

ForeignKeyViolation
      ↓
InvalidReferenceError

ConnectionError
      ↓
PersistenceUnavailableError
```

Database-specific exceptions MUST NOT leak into API responses.

---

# 19. Concurrency

The implementation SHOULD protect against concurrent document updates.

Potential mechanisms:

* unique constraints
* transactions
* row-level locking where required
* optimistic concurrency/version checks

The initial implementation will prefer the simplest mechanism that satisfies the requirements.

---

# 20. Indexing Strategy

Create indexes based on expected access patterns.

Initial indexes:

```text
documents:
    tenant_id
    status
    (tenant_id, source, external_id)

document_versions:
    document_id
    (document_id, version_number)
    content_hash

document_acls:
    document_id
    principal_id

processing_jobs:
    document_version_id
    status

audit_events:
    tenant_id
    resource_id
    created_at
```

Indexes will be reviewed as query patterns evolve.

Conceptually:

```text

      └── PostgreSQL
```

# 24. Cloud Portability

The persistence layer MUST use standard PostgreSQL capabilities wherever practical.

Avoid unnecessary dependencies on:

* AWS RDS-specific functionality
* Azure-specific database APIs
* cloud-specific extensions

Both AWS and Azure will use managed PostgreSQL services with the same application persistence model.

# 26. Risks

### Risk 1 — Overengineering

Do not introduce unnecessary tables or abstractions before they are needed.

### Risk 2 — Database leakage

SQLAlchemy models must not leak into domain/application logic.

### Risk 3 — Cross-tenant access

Tenant context must be mandatory for tenant-owned operations.

### Risk 4 — Search inconsistency

OpenSearch must be treated as derived state.

### Risk 5 — Distributed transactions

Do not attempt to create a transaction spanning PostgreSQL, object storage, and OpenSearch.

Use asynchronous events and reconciliation.

```text
                 Repository Interface
                         │
                         ▼
                PostgreSQL Repository
                         │
                         ▼
                     SQLAlchemy
```

The application should be able to:
